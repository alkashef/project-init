Objective

A high-quality app, A to Z, zero line of code.

  • What does high-quality mean?
    • Code another human can read, understand and change. Code is read far more often than it is written.
    • Readable names, small functions, simple logic, tests that prove it, comments where the why is not obvious.
    • Systems thinking, and proper commit comments that tell the story.
    • A design that is easy to maintain, to change, over time.
  • What does high-quality mean now?
    • The same answer, with a second reader. The AI reads the code, the docs and the comments to know what to do. It changes code faster than anyone can re-read it, and every change lands on the last one.
    • Maintainability. Small mistakes compound. At Basecamp, each vibe-coded PR looked fine alone; together they destroyed the architecture of the system (DHH). Someone has to protect the architecture, and the code has to be easy to protect.
    • Simplicity. beautiful code is easier to understand, it is simpler, it is more malleable (DHH). That holds for the AI too: less to misread, fewer wrong guesses. there is great payoff to writing systems that agents have an easier time dealing with (DHH).
    • Comments. Every AI session starts with no memory. The code shows what it does; only a comment or a doc says why.
    • Systems thinking. The AI writes the part; a person holds the whole: boundaries, data flow, how the pieces fit.
    • Still true: correct, a test for every requirement; safe, no secrets in git, no destructive commands.

What is easy for a person to review is easy for an AI to change.

The three main documents

Spec → Design → Plan

This is a workflow. A way of thinking. Your cockpit for coding.

SpecWhatA human approves

Requirements with IDs. The AI can help write it, interview style.

But a human must review and approve it. This is the single most important step and the single most important quality gate. It is done by a human, not by the AI.

→
DesignHowA human designs

Architecture, data, decisions.

Done by a human; the AI assists. It needs senior software engineering experience.

Milestones with their tests, model, effort and status.

One fact, one file

No copies to drift apart. Finished work leaves the plan.

Works by hand too

Any AI chat, or a person with a text editor. The method is the documents, not the tool.

Around the documents

The workflow, step by step

StepWhatFilesWhy
Inbox You drop ideas, in your words. inbox.md An idea is saved before it is lost. No format to get right.
Spec and design The AI asks only what it cannot decide. You approve the spec. spec.md, design.md What and how are agreed before any code exists. The approved spec is the quality gate.
Plan Milestones, one row each: tests, model, effort, status. plan.md Small steps the AI can finish in one session. Progress is visible at a glance.
Execute One milestone at a time, each in a fresh AI session: tests first → see them fail → build → check → update docs → remove from plan → commit & push. milestone runner, hooks A fresh session keeps the context small. Hooks run the checks, so nothing depends on the AI remembering.
Blocked Needs your decision? The question goes in the plan. Nothing else changes. plan.md The AI never guesses at a decision that is yours. The question waits in the repo.
Approval Your answer goes in the plan. Commit, run again. plan.md The decision is recorded, so the next run and the next reader know why.
Always on CLAUDE.md + rules about 190 lines; topic rules load per file Hooks each edit: lint & fix; each commit: all checks & tests Permissions allow routine, ask risky, deny destructive

The skill sets all of this up in one command: files, git, GitHub, environment, tools.

What you get, and why

Enforce with tools, not prompts

ToolEnforces

Prettier · StylelintFormatting, CSS rules
mypy · tscStrict types
pytestBehavior, 80% branch coverage
Git hookAll of the above, on every commit
PermissionsNo force push, no hard reset

A prompt is advice

Probabilistic. The same prompt can give a different result each time.

  • Followed most of the time.
  • Costs context in every session.
  • The longer it gets, the less it is followed.

A linter1 is a rule

Deterministic. The same code always gets the same verdict.

  • Enforced every time.
  • Costs nothing until it fails.
  • Runs in under a second.

If a tool can check it, it goes in the tool's config. CLAUDE.md keeps only what no tool can check, in under 200 lines.

1 Linter: a program that reads your code without running it and flags style problems, likely bugs and code smells against a fixed set of rules. Many can also fix what they find. Examples: ruff for Python, ESLint for JavaScript.
